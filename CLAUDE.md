# TuTurno PWA — La Purísima Conchi

SPA React 19 + Vite 6 + Tailwind 3 + React Router 7. Backend: Firebase Realtime Database + Auth (sin Firestore) y funciones serverless de Vercel en `api/`. Pagos con Redsys. Sin TypeScript ni tests automatizados. El README tiene la documentación técnica general; aquí solo lo que conviene saber antes de tocar código. Texto de interfaz, nombres y comentarios van en español.

## Comandos

```bash
npm run dev      # http://localhost:5173
npm run build
npm run lint     # hay errores y avisos previos ajenos a tus cambios: no los arregles de paso
npm run migrar-categorias -- --project <proyecto> [--instance <bd>] [--dry-run] [--yes]
```

## Entornos: cuidado con producción

- **Sin `.env.local` la app apunta a PRODUCCIÓN** (Firebase y `/api`). Para trabajar contra staging copia `.env.example` a `.env.local` (no se sube a git; contiene `VITE_FIREBASE_*`, `VITE_ENV=staging` y el proxy de `/api`).
- Staging: proyecto `la-purisima-conchi-staging`. Producción: `la-purisima-conchi`. `.firebaserc` apunta a producción por defecto, así que pasa siempre `--project` a la CLI de Firebase.
- Reglas de la base de datos: `database.rules.json`. Despliegue a staging: `npx firebase-tools deploy --only database --project la-purisima-conchi-staging`. Antes, `npm run probar-reglas` (emulador, hace falta Java; `scripts/probar-reglas.mjs`): añade casos si cambias una regla. No despliegues a producción ni ejecutes migraciones contra producción sin que lo pida el usuario.
- Ramas: `main` y `staging`. Toda rama nueva (también las de worktrees) sale de `origin/staging`, nunca de `main`: haz `git fetch origin` antes y, si la rama no parte de ahí, rebásala o recréala. Las PR de trabajo van contra `staging`. Commits y PR en español.
- Administradores: `src/utils/administradores.js` y `database.rules.json` (mismos dos emails; si cambia uno, cambia el otro). Además hace falta el **email verificado** (`auth.token.email_verified`, también en `api/`): `RutaAdmin` enseña a un admin sin verificar cómo hacerlo.

## Reglas de la base de datos

Van por ruta: nunca una regla general (`auth != null` o similar) en la raíz de una colección.
- `usuarios/{uid}`: cada persona lee su nodo y escribe campo a campo (usa `update`, no `set`, sobre `usuarios/{uid}`), menos `bonos` y `tarjetasRegalo`, que solo escribe el servidor.
- `reservas`, `reservasGrupos` y `pedidosPendientes`: el navegador solo **crea** nodos nuevos a su nombre, pendientes de pago y sin los campos que decide el servidor (`reservadaHasta`, `codigoReserva`, `cancelacionEstudio`…); no lee, no cambia ni borra. Leer reservas para contar plazas va por `api/disponibilidad.js` (`src/utils/disponibilidad.js` y `contarPlazasDia.js`: solo un admin lee la base de datos).
- `tarjetasRegalo` y `codigosTarjetaRegalo`: solo servidor. Comprobar un código, canjear una tarjeta (confirma las reservas pendientes del pedido y crea el bono) y reservar con un bono van por `api/codigo-reserva.js` (`tipo` `tarjeta`, `canjear`, `usarBono`; lógica en `api/_canjeServidor.js`, llamadas en `src/utils/canjeServidor.js`).
- Notas, solicitudes, `notificaciones`, `tarjetas_regalo`: solo admin. `bloqueosFechas` y `fechasHabilitadas`: lectura pública, escritura admin, como `clases` y el resto de configuración.

## Modelo de datos (Realtime Database)

- `clases/{id}`: talleres. Los creados desde el panel llevan `dinamica: true`, `grupo` (id de categoría), `categoria` (etiqueta), `reservasPath`, etc. Los "de siempre" tienen página propia (`CreaTu*.jsx`, `Reserva*.jsx`) y su ficha en `clases/{id}` guarda la configuración editable desde el panel.
- `reservas/{reservasPath||id}/{fecha}/{turno}[/{metodo}]/{reservaId}`. El aforo solo cuenta reservas `Confirmada` y pagadas. Un taller migrado conserva su carpeta antigua en `reservasPath`, por eso migrar nunca mueve ni toca reservas.
- `imagenesClases/{id}`: fotos de los talleres dinámicos (en la base de datos, no hay Storage).
- `categoriasTalleres/{id}`: `{titulo, descripcion, orden, estado: activa|oculta, migrada?, eliminada?, creadoEn, actualizadoEn}`. Lectura pública, escritura solo admin. Si las reglas no están desplegadas, `src/categoriasTalleres.js` avisa una vez y devuelve lista vacía en vez de romper.
- El webhook `api/notificacionTPV.js` localiza la reserva por número de pedido recorriendo `reservas/`; no depende de qué página la creó. Es una URL pública: solo confirma si la firma de Redsys es válida (`api/_firmaRedsys.js`, la misma que usa `api/crear-sesion.js`); no la relajes y prueba cualquier cambio de firma en staging con el TPV de pruebas. `api/pago-admin.js` deja a un admin simular la confirmación de un pago.

## Piezas clave

- **Compra sin registro**: cada compra de invitado abre una sesión anónima de Firebase (hay que tener activado el proveedor Anónimo). En `/reservar/:id` la sesión **no se abre al entrar**: la pantalla se ve sin sesión (`AccesoCompra permitirVisita`), lee la disponibilidad de `api/disponibilidad.js` (`src/utils/disponibilidad.js`; también con sesión: solo un admin lee la base de datos) y pide nombre, email y teléfono al pulsar «Confirmar y pagar» (`DatosContactoInvitado` → `iniciarCompraInvitado`). Las reglas del conteo de plazas están en `src/utils/plazasOcupadas.js`, compartidas por el navegador y la función; esa función solo devuelve fechas y números, nunca datos personales, y su lógica vive en `src/utils/disponibilidadServidor.js`. En `npm run dev`, `/api/disponibilidad` va al Vercel del proxy como el resto de `/api`. El resto de pantallas de reserva y pago piden los datos al entrar, como antes. `src/utils/invitado.js` + `src/AccesoCompra.jsx` la mantienen mientras se navega por reserva/pago (clave `compraInvitado` en `sessionStorage`) y la cierran al salir o en `ConfirmacionPago`/`PagoFallido`. No se recuerdan datos entre compras (decisión del cliente). Al registrarse se conserva el uid (`linkWithCredential`). **Los bonos y los productos que se gestionan desde el perfil exigen cuenta**: `exigeCuenta(clase)` en `src/catalogoTalleres.js` (bono, o `requiereCuenta: true` en la ficha, casilla del formulario del taller); `AccesoCompra requiereCuenta` salta el formulario de invitado, `AccesoCompraTaller` lo decide para `/reservar/:id` y las rutas de bonos de siempre y `/usar-bono/*` lo llevan fijo en `App.jsx`. Un bono comprado como invitado quedaría huérfano en una sesión anónima que no se puede reabrir.
- **Cambio de fecha sin sesión**: cada reserva pagada (individual o de grupo) tiene un código `K7M3-9QXP` (`api/_codigosReserva.js`; índices `codigosReserva/{codigo}` y `codigosPorPedido/{pedido}`, solo `firebase-admin`). Se crea en el aviso del TPV y en `pago-admin.js`, y al pedirlo con `api/codigo-reserva.js` (lo enseña `ConfirmacionPago` con `components/CodigoReserva.jsx`). `/gestionar-reserva` (`GestionarReserva.jsx`) + `api/cambiar-fecha.js` cambian la fecha con código + email: un solo cambio, 72 h de antelación, aforo y bloqueos como en el panel; las reglas están en `src/utils/cambioFecha.js` (sin SDK). Un número de pedido antiguo (solo dígitos) también entra y crea el código. Los grupos solo cambian si están `Confirmada` y quedan marcados `cambioClientePendienteRevision`. El código también va en el correo de confirmación (ver más abajo) y se enseña en pantalla. Las reservas de la pantalla antigua `ReservaConTarjetaRegalo` (`reservasTarjetaRegalo/…`) no se pueden cambiar así.
- **Cancelación por el estudio y volver a reservar**: al cancelar una reserva individual en el detalle del panel (`AdminDetalleReservaNuevo.jsx`, que escribe la marca «Cancelada» en el navegador) hay una casilla «Avisar al cliente por correo» (marcada por defecto). Después llama a `api/codigo-reserva.js` con `tipo: "cancelacion"` (solo admins; la lógica está en `api/_cancelacionReserva.js`): asegura el código, deja la reserva recuperable (`cancelacionEstudio`, `recuperada: false`, `recuperableHasta` = hoy + `MESES_RECUPERACION`, 6, en `src/utils/cambioFecha.js`) y, si se pidió, envía el correo (`construirCorreoCancelacion` en `api/_correoReserva.js`: motivo, código y botón; con cuenta lleva a `/perfil`, sin cuenta a `/gestionar-reserva`). Desde el mismo detalle se puede enviar o reenviar el correo más tarde. `evaluarCambio` deja una reserva así cambiar de fecha sin el plazo de 72 h ni el límite de un cambio; `api/cambiar-fecha.js` la pone otra vez `Confirmada` en la nueva fecha (`recuperada: true`, sin contar como cambio del cliente). En el perfil, `AvisoCancelacion` enseña «Elegir nueva fecha», que abre `/gestionar-reserva?codigo=…&auto=1` con el email de la cuenta y busca sola. Al cancelar hay otra casilla, «Permitir que el cliente vuelva a reservar» (marcada por defecto): sin ella la reserva queda cancelada del todo (`permitirReprogramar: false`, sin código en el correo) y desde el detalle se puede quitar la opción más tarde. No cubre grupos (`reservasGrupos`) ni reservas sin número de pedido.
- **Talleres desde el panel**: `/admin-taller` (`AdminTallerForm.jsx`, usado también para editar desde el detalle de clase), páginas genéricas `/taller/:id` y `/reservar/:id`. Los de siempre se pasan al panel desde `/admin-migrar-talleres` (`src/migracion/migrarTalleres.js`, reversible por taller; las rutas antiguas redirigen con `RutaTaller`/`RutaCategoria`).
- **Categorías**: las cuatro de siempre viven en código (`src/categoriasDeSiempre.js`: `crear_piezas`, `pinta_decora`, `cursos_bonos`, `otros`) hasta que se migran a `categoriasTalleres` (panel `/admin-categorias` o `scripts/migrar-categorias.mjs`, idempotente y de un solo sentido). `src/categoriasTalleres.js` es la única puerta de acceso: úsala en vez de leer `categoriasTalleres` a mano. `cursos_bonos` no se puede borrar. Una categoría solo se borra si no tiene talleres (ocultos incluidos).
- **Piezas comunes de las reservas** (`ReservaTallerDinamico` y `ReservaBonoDinamico`): `PantallaReserva` (tarjeta, ancho `max-w-4xl` para dos columnas), `SelectorDiaReserva` (calendario y avisos del día), `SelectorTurnoReserva`, `BotonConfirmarReserva` en `src/components/`, y el hook `useDiaDeReserva` en `src/utils/turnosTaller.js` (turnos, día bloqueado, habilitado a mano, sin taller). La lógica de cada producto (método y plazas en talleres; precio, casilla de torno y primera sesión en bonos) sigue en su pantalla.
- **Bonos y primera sesión**: al comprar un bono (`ReservaBonoDinamico`) se reserva su primera sesión: reserva `desdeBono` en `reservas/…` con el `orderId` del pedido, pendiente hasta el pago (con tarjeta regalo la confirma el servidor al canjearla, `api/_canjeServidor.js`), y el bono nace con esa clase consumida (`datosPrimeraSesionBono` en `src/utils/estadoBono.js`, sin SDK, compartido con el servidor). El aviso de Redsys (`api/notificacionTPV.js`) y el pago simulado por admin (`api/pago-admin.js`) la confirman con `confirmarPrimeraSesionBono` (`api/_primeraSesionBono.js`), que es idempotente y no hace nada con pedidos anteriores sin esa reserva. Las demás clases se reservan desde el perfil con `UsarBono`, que llama al servidor (`tipo: "usarBono"`: comprueba bono, bloqueos y aforo, y descuenta la clase con una transacción). Solo cubre los bonos migrados al panel (las pantallas de bono de siempre no lo hacen).
- **Correo de confirmación**: `api/_correoReserva.js` envía el email con Resend (`fetch`, sin dependencias) al confirmarse una reserva de taller, un bono o una tarjeta regalo (`tipo`: `reserva`, `bono`, `tarjeta_regalo`): desde `api/notificacionTPV.js` y `api/pago-admin.js` y, para lo que se canjea con tarjeta regalo, desde el propio canje (`api/_canjeServidor.js`). **Vercel limita a 12 funciones por proyecto** (los archivos de `api/` sin `_`): hoy hay 8; antes de añadir otra mira si cabe en una existente, y no subas copias (`*-backup.js`) ni endpoints de depuración, que también se despliegan y son públicos. Todos llevan el código de reserva corto (`K7M3-9QXP`, `api/_codigosReserva.js`); bonos y tarjetas regalo lo reciben al enviar el correo. Una sola vez por pedido (marca en `correosEnviados/{orderId}`, solo servidor) y nunca rompe el pago. Variables de Vercel: `RESEND_API_KEY`, `CORREO_REMITENTE` (dominio verificado), opcionales `CORREO_COPIA_ADMIN`, `CORREO_RESPONDER_A` y `CORREO_URL_BASE` (logo y enlace al perfil). Sin `RESEND_API_KEY` no se envía nada. No cubre pagos individuales de grupo ni `UsarBono`.
- **Espacio y aforo real**: `/admin-espacio` (`AdminEspacio.jsx`) edita `configuracionEspacio` (lectura pública, escritura admin; `src/utils/configEspacio.js` + `src/configuracionEspacio.js`): aforo total por franja, tope de torno, mínimo de personas para reservar en grupo (global, 3), minutos que se guarda la plaza al pagar (15) y horarios por defecto de los talleres nuevos. El aforo es común a todos los talleres y los grupos: `src/utils/aforo.js` cuenta por franja (fecha + turno, sumando también los turnos que se solapan con él: 10:00-12:00 y 11:00-13:00 comparten plazas) las reservas confirmadas, los grupos confirmados y las pendientes con `reservadaHasta` en el futuro (`incluyeTorno` marca las que usan torno). Las reservas de `/reservar/:id` y de la primera sesión de un bono las crea el servidor (`api/_reservarServidor.js`, acción `reservar` de `api/codigo-reserva.js`): escribe, vuelve a contar con lo que llegó antes y, si no cabe, borra y avisa; en `npm run dev` sin la función desplegada se escribe directo. Si un pago llega con la plaza caducada y la franja ya está llena, se confirma igualmente y se marca `sobreaforo` (`marcarSobreaforo`, visible en el detalle de la reserva). El cron semanal borra las pendientes caducadas. Las pantallas `Reserva*` de siempre no comprueban este aforo. `plazas.maxTotales/maxTorno` de la ficha ya no se usan en los talleres del panel.
- **Mínimos de personas**: dos números distintos. `minPersonasGrupo` de la ficha del taller (`minPersonasHabilitar(clase)`, por defecto 5) es lo que hace falta para habilitar un día sin horario (días «solo grupo» de `ReservaTallerDinamico`); el mínimo de una reserva de grupo es el global de `configuracionEspacio`. Un grupo confirmado ya no abre turnos.
- **Bloqueos por horas**: `bloqueosFechas/{fecha}` puede llevar `turnosBloqueados` (rangos `HH:MM-HH:MM`; vacío = día entero). Un turno se bloquea si se cruza con un rango (`src/utils/rangosHora.js`). Las pantallas nuevas, el servidor y el cambio de fecha lo respetan; las `Reserva*` de siempre ven `bloqueado: true` y bloquean el día entero.
- **Talleres monográficos** (`monografico: true` en la ficha, `src/utils/monografico.js`): sin horario semanal, con `ediciones` (grupos de `sesionesCurso` sesiones, cada una con fecha y turno: un día puede tener dos) que se reservan enteras en `ReservaMonografico.jsx` (un pago, una reserva por sesión con el mismo `orderId`, `edicionId`, `fechasEdicion`). Solo se reservan antes de la primera sesión; el taller se oculta (`estadoPublico`) cuando ya no queda ninguna edición por empezar. `/gestionar-reserva` cambia a otra edición con plazas (`resolverEdicion` en `api/cambiar-fecha.js`). Cada sesión lleva su marca `torno`, que decide si cuenta en el tope de torno. Se pagan con tarjeta regalo, no con bono.
- **Talleres de varias sesiones** (`sesiones` > 1 en la ficha, sin ser monográficos): en `/reservar/:id` se pueden reservar todas las sesiones de una vez (`SesionExtraReserva`, mínimo de días entre cada sesión y la siguiente: `diasEntreSesiones` de la ficha, una lista [1ª-2ª, 2ª-3ª…] (o un solo número en fichas antiguas), por defecto 28; `src/utils/sesionesTaller.js`) o solo la primera, dejando el resto para más adelante (`segundaSesion`, como siempre). Cada sesión es una reserva con el mismo `orderId` y `sesionCurso`/`sesionesCurso`/`fechasSesiones`; el precio va en la primera. `api/_reservarServidor.js` valida número de sesiones y días mínimos y comprueba el aforo de todas. Con el código, `/gestionar-reserva` lista las sesiones y deja cambiar cada una por separado (un cambio y 72 h por sesión, respetando esos días con las vecinas: `resolverSesiones` en `api/cambiar-fecha.js`). Las reservas de «solo la primera» siguen sin poder cambiarse online.
- **Header global** en `src/Header.jsx`, montado desde `AppLayout.jsx`. En staging `main.jsx` muestra una banda naranja "entorno de pruebas".

## Al cambiar cosas

- Si añades una ruta de reserva/pago para invitados, envuélvela con `AccesoCompra` y revisa `database.rules.json`.
- Si cambias `database.rules.json`, dilo en la PR: hay que desplegarlo a mano en cada proyecto.
- Al verificar en el navegador contra staging, las reservas de prueba que crees quedan en la base de datos de staging; no uses producción.
